## 单元测试方案

### 单元测**试**流程

1. **准备阶段**：环境配置、框架选型、目录结构规范。

   - ​**目标**：为团队建立统一的测试框架、目录结构和构建配置。
   - ​**操作步骤**：

     1. **选定框架**：根据项目特性选择测试框架（如Google Test + Google Mock）
     2. ​**配置覆盖率工具**​：确保构建系统支持`Coverage`​模式，添加编译选项`-fprofile-arcs -ftest-coverage`​，并安装`lcov`。
     3. ​**建立目录规范**​：在项目根目录创建`test/`​，内部按生产代码的模块结构镜像组织测试文件（如`test/module_a/`​），并预留`mocks/`​、`fixtures/`​、`data/`子目录。
     4. ​**定义质量门禁**：与团队约定初始覆盖率阈值（例如行覆盖率≥70%），并作为后续CI检查的依据。
2. **开发阶段**：TDD或编写测试与代码并行，包括设计可测试代码、编写测试用例、使用Mock。

   - ​**目标**：遵循“可测试性”原则，同步或先行编写单元测试。
   - ​**操作步骤**：

     1. ​**设计可测试接口**：采用依赖注入，将外部依赖（[[数据库]]、网络等）抽象为接口，便于Mock。
     2. ​**编写测试用例（TDD可选）** ：

        - 针对每个函数或类，设计​**正常路径**​、​**边界条件**​、**异常场景**的测试。
        - 使用**Arrange-Act-Assert**模式组织测试函数。
     3. ​**实现Mock对象**​：对接口使用GMock定义预期行为（`EXPECT_CALL`）
3. **执行阶段**：本地运行测试，调试，确保通过。

   - ​**目标**：在提交代码前，确保所有测试通过且覆盖率满足团队最低要求。
   - ​**操作步骤**：

     1. **运行全部单元测试**：确保没有因修改引入回归
     2. **生成本地覆盖率报告**：

        ```cmake
        # 进入Coverage构建目录（假设已配置）
        [[CMake]] -B build_coverage -DCMAKE_BUILD_TYPE=Coverage
        [[CMake]] --build build_coverage
        cd build_coverage
        ctest
        lcov --directory . --capture --output-file coverage.info
        lcov --remove coverage.info '/usr/*' '*/test/*' '*/googletest/*' -o coverage.filtered.info
        genhtml coverage.filtered.info --output-directory coverage_report
        ```
     3. **审查未覆盖代码**：打开`coverage_report/index.html`，查看哪些行未被覆盖，补充必要测试。
     4. **提交代码**：确保本地所有测试通过后，提交PR/MR
4. **集成阶段**：提交代码，CI中自动构建并运行测试，收集覆盖率，生成报告。

   - ​**目标**：在CI服务器上自动构建、运行测试、收集覆盖率，并作为合并的门禁。
   - ​**操作步骤**：

     1. ​**触发CI流水线**：代码推送后，CI工具（如GitHub Actions、[[Jenkins]]）检出代码。
     2. ​**构建测试环境**：安装依赖（如lcov、[[CMake]]），配置Coverage构建类型。
     3. ​**编译并运行测试**​：执行`ctest`，若测试失败则流水线中断并通知。
     4. ​**生成覆盖率报告并上传**：

        - 使用`lcov`生成过滤后的覆盖率数据。
        - 上传到覆盖率托管平台（如Codecov、SonarQube）或作为CI artifact存档。
     5. ​**质量门禁检查**：

        - 平台比较当前覆盖率与基线（如目标分支），若新代码覆盖率低于阈值或整体覆盖率下降，则标记为“未通过”，阻止合并。
5. **质量反馈阶段**：审查覆盖率报告，确保满足门禁，若未通过则反馈给开发者。

   - ​**目标**：将测试结果可视化，驱动团队持续提升测试质量。
   - ​**操作步骤**：

     1. ​**查看趋势报告**：在覆盖率平台（如Codecov）上查看历史趋势，关注模块级别的覆盖率变化。
     2. ​**PR评论自动提示**：CI机器人可在PR中评论新增代码的覆盖率，提醒开发者补充测试。
     3. ​**定期复盘**：每月召开测试质量会议，分析覆盖率盲区和失败案例，识别高风险模块并定向补充测试。
     4. ​**利用AI辅助**：

        - 对于覆盖率低的函数，使用大模型（如DeepSeek）自动生成候选测试用例，人工审核后合并。
        - 使用AI分析测试代码质量，如识别缺少断言的“空测试”。

### 主流测试框架选型

|框架|优势|劣势|适用场景|
| ------| ---------------------------------------------------------------------------------------------| -------------------------------------------------------| ----------------------|
|**Google Test ([[gtest]])**|工业级标准，功能最全（断言、装置、死亡测试）；自带 ​**Google Mock (GMock)** ，Mock功能强大；社区活跃，文档丰富。|相对较重，编译较慢；配置比单头文件框架稍复杂。|​**大型企业项目**​、​**需要复杂Mock的场景**​、​**对稳定性要求极高的系统**。|
|**Catch2**|现代化的语法（如`SECTION`​），可读性强；支持BDD风格（`GIVEN-WHEN-THEN`）；单头文件版本(v2)集成简单。|v3版本不再单头文件；Mock需第三方库（如Trompeloeil）。|​**追求现代C++语法体验**​、​**中型项目**​、**希望编写高可读性测试**的团队。|
|**Doctest**|​**编译速度极快**；同样单头文件设计；功能却非常接近Catch2。|社区和生态系统相对[[gtest]]较小。|​**对编译时间极其敏感的大型代码库**​、​**希望将测试内联在头文件中**。|
|**Boost.Test**|功能极其丰富，与Boost库集成紧密。|依赖Boost库；学习曲线较陡；编译较慢。|**已重度使用Boost库**|

## 测试数据管理

代码内数据：简单测试直接在测试文件中定义常量

外部文件：复杂数据（如JSON、XML、大块文本）放入test/data/，在测试中读取。[[CMake]]需配置工作目录，确保运行时能找到文件。

```cmake
// 在测试中获取文件路径
#include <filesystem>
std::filesystem::path testDataDir = std::filesystem::path(__FILE__).parent_path() / "data";
```

‍

#### **并行测试执行优化**

使用 `gtest-parallel`​ 或 [[CMake]] 的 `ctest -j N` 来并行运行测试，大幅缩短执行时间。

bash

```
# 安装 [[gtest]]-parallel ([[python]]脚本)
pip install [[gtest]]-parallel

# 运行，启动4个并行进程
[[gtest]]-parallel ./build/my_library_test -w 4 --gtest_filter=*
```

## AI辅助测试

AI可以辅助评估测试质量，超越单纯的覆盖率：

- ​**测试断言密度**：断言数量与测试代码行数的比例。
- ​**变异得分（Mutation Score）预测**：AI可预测生成的测试能杀死多少变异体（注入的故障），以此衡量测试的有效性。
- ​**需求一致性**：AI可以对比测试用例和需求文档（或代码注释），评估测试是否验证了预期的功能点。

#### **工具推荐**

- ​**通用大模型**​：​**DeepSeek**​, ​**GPT-4**​, **[[Claude]]** 等，通过API集成到内部工具链中。
- ​**学术/实验框架**​：关注如 **TestLoter** 这类研究框架，它通过逻辑驱动的思维链和分层修复机制，展示了LLM在生成高覆盖率和可编译测试方面的潜力。

### **实施步骤与时间线建议（6-8周）**

- **第1周：基础设施搭建**

  - 选定测试框架（建议[[gtest]]）和覆盖率工具（gcov/lcov）。
  - 改造CMakeLists.txt，集成FetchContent下载[[gtest]]。
  - 配置CI流水线（如GitHub Actions），至少能编译通过。
- **第2-3周：单元测试大规模引入**

  - 团队培训：[[gtest]]/GMock核心概念、测试编写规范。
  - ​**攻坚阶段**：为核心模块（如算法、工具类）编写第一批高覆盖率单元测试，目标行覆盖率>60%。
  - 引入并行测试，优化执行时间。
- **第4周：覆盖率门禁与可视化**

  - 集成lcov，在CI中自动生成覆盖率报告并上传至Codecov。
  - 设置质量门禁：PR新增代码的行覆盖率不得低于​**80%** 。
- **第5周：集成测试场景开发**

  - 针对核心业务流（如“下单-支付”），设计并实现1-2个关键集成测试场景。
  - 搭建Docker Compose测试环境（如App + PostgreSQL）。
- **第6周及以后：AI试点与优化**

  - 选择1-2个新开发模块，试点用大模型辅助生成测试用例，评估效率提升。
  - 尝试用AI分析现有覆盖率报告中的盲区，并人工评估AI生成补丁用例的有效性。

‍

- **核心指标**：

  - ​**行覆盖率 (Line Coverage)** ：目标 >= 75%（核心模块 >= 85%）。
  - ​**分支覆盖率 (Branch Coverage)** ：目标 >= 60%。更能反映逻辑覆盖的完整性。
  - ​**测试通过率**：CI上必须100%通过。
  - ​**测试执行时间**：监控趋势，防止因测试膨胀导致CI等待时间过长。
- ​**监控方案**：

  - 使用 **Codecov / SonarQube** 等平台展示覆盖率历史趋势。
  - 在CI中，当覆盖率下降超过1%时，自动在PR中添加警告评论。
  - 建立定期的“测试质量复盘”，利用AI分析报告，找出最“脆弱”或最“未被测试”的模块，定向改进。
